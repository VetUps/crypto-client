# Crypto client — развёртывание

REST API на FastAPI + фоновое обращение к Deribit API на Celery

```
            ┌─────────┐
 client ──▶ │  app    │──┐
            │ (FastAPI)│  │
            └─────────┘  ▼
                   ┌──────────┐      ┌─────────┐
            ┌────▶ │  redis   │◀──── │  beat   │  (планировщик)
            │      └──────────┘      └─────────┘
            ▼           │
      ┌──────────┐      ▼
      │ postgres │  ┌─────────┐
      └──────────┘  │ worker  │  (исполнители)
                    └─────────┘
```

Redis — брокер сообщений для взаимодействия beat и worker.
Postgres — единственное источник правды, его не трогают ни worker, ни beat напрямую… (опиши свою реальность).

# Design decisions

### 1. Одна таблица `prices` без отдельной для валют
По ТЗ требуется всего 2 тикера (BTC, ETH). Отдельная таблица привела
бы к лишним join-ам при каждом запросе. При масштабировании до 100+ валют следует добавить справочник и нормализацию.

### 2. Hash индекс на колонку `ticker`
Hash иднекс на ticker. Так как нам часто нужно будет искать записи на точное соответствие по ticker-у, а также проверять наличие крипты по ticker-у, было принято решение накинуть hash индекс на эту колонку, что поднимет производительность на больших данных.
Составной индекс для ticker + timestamp может рассматривается для будущих версий.

### 3. Repository pattern
 Паттерн Repositroy. Реализован для разделения бизнес-логики от слоя работы с данными. 
 Также хорошее решение на будущее, если захочется поменять Postgres на что-то другое, что кстати хорошо для тестов. 
 Реализовано не идеально, по крайней мере не нужно будет менять много кода.

### 4. Сервисный слой между FastAPI и Repository
FastAPI работает только с HTTP, а бизнес-логика вынесена в сервисы. 
Это позволяет переиспользовать ту же логику в Celery задачах и упрощает тестирование.
Ну и также делает код чище.

### 5. Два движка SQLAlchemy: async для FastAPI, sync для Celery
Два движка алхимии: для FastAPI и Celery. Не прям систем-дизайн решение, а просто как то, что я узнал что-то новое про движки в алхимии. Так как вся система асинхронная, здесь есть event loop-ы, а движок привязывается к первому запущенному event loop-у. Из-за того, что celery заточен под синхронные задачи, приходиться для каждой задачи самому запускать новый event loop, что вызывает проблемы с переиспользование движка.

### 6. Redis как брокер
Для подобной задачи, как "вытянуть что-то с внешнего API раз в минуту" RabbitMQ или Kafka был бы избыточен.
Redis проще в эксплуатации и полностью покрывает требования.
